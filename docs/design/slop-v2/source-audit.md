## URL and navigation contracts

- `/wallet` becomes `/account#wallets`; `/verification` becomes `/how-it-works#verification`. `canonicalPath` preserves query text and replaces history. They are compatibility destinations, not extra canonical pages.
- `/points?x` renders Account regardless of the value. Account anchors are `#profile`, `#connections`, `#wallets`; `/points#rules` and `/points#people` preserve earning and discovery access.
- Homepage anchors include `#projects`, `#featured-projects`, `#community-projects`, `#leaderboard`, `#how-it-works`. Project `#start` is installation/participation; `#contributors` is shared standings. Funding `#payouts` selects Manage payouts; no fragment selects Records. Verification is an expanded detail state at `#verification`.
- Shared standings (`Points.tsx:876–949`) serialize `sort=points|money` (default score omitted), `period=lifetime` (default month omitted), `cohort=new` (default all omitted), `q`, `project` on global views, and one-based `page`. Legacy `period=new` maps to lifetime + new cohort. Project standings bind the project instead of persisting another project filter.
- Archive (`CyclePages.tsx:370–411`) preserves `project`, `month=YYYY-MM`, `state` with bounded parsing and back-navigation restoration.
- Login `next` (`Points.tsx:99`) accepts same-origin paths including query/fragment, rejects external/protocol-relative/backslash/login destinations, and supports legacy `next=earnings`. Show a clear local return destination; a denied provider action returns to the preserved draft.
- `Link.tsx:13–69` handles fragment scrolling and internal navigation. Deep links need focus/scroll behavior as well as matching screens. Unknown fragments must not masquerade as selected tabs.
- Matcher normalizes repeated/trailing slash segments and catches malformed percent decoding. Its `/projects/new` branch currently checks the first two segments without exact length: this is source behavior to record, not design approval for arbitrary new subroutes.
- Raw Markdown, manifest/policy/source GitHub links, installer/archive/checksum downloads are functional destinations outside page frames. Inventory them in the parent coverage artifact; preserve exact bytes/version/digest relationships.

## Project and resource variants

Read `projects/*/project.json`; never duplicate a second runtime inventory. At the audited SHA all twelve manifests declare `committedMinor: "0"`; monthly projects disable payment. Existing active monthly examples (ASI, Eliza), active external-prize example (Delta Star), and paused community projects must not be styled as funded opportunities. IDs/names in this document are audit examples, not a new registry.

Required variants: monthly versus external-prize share; active versus paused; archived with successor; restricted/permission-gated; featured versus community; unknown/mixed license facts; no work versus bounded available work versus ineligible/claimed work; reward window not started; live/closed cycle; disabled payment versus reviewed policy target. Archived/restricted scenarios are design coverage even when absent from current manifests. A registered paused project is listed but uncollected; empty accepted work is not evidence of ingestion failure. Do not infer legal ownership from stewardship.

Data ownership: `use-public-resource.ts` and `Presentation.tsx:9` provide resource/retry notices; App selects snapshot requirements per route. Home and settings have independent resources; cycle archive uses the cycle index; funding uses its index; earnings uses the payment backend. One successful resource cannot clear a failed dependency. Retain timestamp, coverage window/count and evidence references when stale data is available.

## Flow inventory for prototype coverage

1. Discovery → project status → bounded work → skill/copy/download → live GitHub recheck → GitHub contribution. Outside issue authorship/submission remains human controlled. Maintainer acceptance is a separate step; no auto merge.
2. Login → safe return → Account profile/visibility → optional X connect → Wallets. Branches: signed out, provider denied/unavailable, interrupted draft, private membership, X hidden, save failed. Optional X/trace never blocks contribution.
3. Wallet address/network → public-registration consequence → exact destination confirmation → possession/signature → pending/saved/error. Separate wallet control, authenticated actor identity and approved payout binding; no wallet login or key entry.
4. Earnings → reserved/no-wallet/wrong-network/held → correct-chain registration → eligible-dispatch target → submitted/uncertain/finalized receipt. Automatic dispatch is a gated escrow target, not a live prototype capability.
5. Project proposal → repository lookup → facts/unknown license → reward/policy → preview → GitHub handoff → review/publication pending. Draft persists; failed lookup leaves facts unknown. Update flows reuse fields. No draft appears activated.
6. Public funding Records ↔ Manage payouts → select complete cycle → review/edit/search/paginate recipients → approval/evidence blockers → export unsigned legacy handoff → scheduled versus verified paid. Human GitHub review and on-chain authority remain external prerequisites.
7. Approved escrow target: sponsor deposit → funded reserves → owner approval → exact binding → test execution → finality; unused withdrawal shows protected obligations and 10% fee. Label as gated policy scenario; donation funding disabled.
8. Ranking filters → public person → combined activity → source receipt/cycle → exact evidence. Missing usage is unavailable, not zero; Points, Slop Score, allocation weight and verified money received remain separate.
9. Cycle archive filters → frozen cycle → Suggested/Approved/Paid → review dates/history/artifacts → appeals/recovery destination. Historical fee/network rules remain frozen.
10. How it works → verification details → invalid input/retry/derived result. Models → client local view/diagnostics → exact declaration/source receipt. Sponsors → project comparison → funding terms → unavailable next action.

## Inventory gaps and design boundary

PRD section 16 also proposes `/leaderboard`, `/admin`, legal/help/status pages and Account sessions/notifications/recovery. Those are required-target concepts with unresolved implementation and permissions, not additional implemented routes in the 17-page source baseline. Account source presently has profile/connections/wallets and an Earnings link. A complete source-route redesign does not prove every future target screen exists. Parent coverage records must explicitly distinguish these targets, compatibility URLs, external artifacts and current route frames.

The audited source used `development` → reviewed `main` while the instructions supplied for this design task require `develop`. The ProjectUpdatePage generated brief also contains a `develop` target (`ProjectProposalPage.tsx:1490` vicinity). This is a source/instruction conflict for maintainers to reconcile; the supplied instructions govern this task. Design handoffs say “reviewed PR” without choosing a deployment policy. No branch or deployment setting is changed.
